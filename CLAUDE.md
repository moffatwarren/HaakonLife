# Haakon Life

A Game Boy-style walkabout of the Haakon office in the browser, with about 60 mini-games, live
multiplayer and seasonal events. Played by real coworkers at haakonlife.com. `README.md` is the full
manual: every feature, the `#play` test shortcuts, and how each part works. Read the part you're
changing, and update it in the same change.

| Where | What |
| --- | --- |
| `js/game.js` | Nearly everything, as one big function: the world, UI, every mini-game, multiplayer. Sections start with `// ---------- name ----------` |
| `js/art.js`, `js/lot.js` | Pixel art: characters and office, and the parking lot |
| `js/maps.js` | Generated by `tools/build_maps.py`. Edit that, never this |
| `js/people.js`, `js/music.js`, `js/font.js` | Coworkers and their lines, songs, the font |
| `js/hockey.js` | Hockey's rules with no drawing or keys: see "Games that might go multiplayer" |
| `server/` | The game server (Node + `ws`): who's here, messages, `games/` (two-player matches), `tables/` (anyone can join) |
| `tools/` | Map builder, checks, screenshots, backups, and `test.html`, the page for testing |

## Going live

**A push to `main` goes straight to real players, so don't push unless asked.**

- **Site:** `.github/workflows/deploy-site.yml` runs `tools/check_games.mjs`, then uploads to the
  Namecheap hosting by FTP, one file at a time.
- **Upload list:** the upload takes everything it isn't told to skip, so a new file at the top of the
  repo goes on the public website unless it's added to `exclude` in that workflow.
- **Server:** Render deploys it from `main` on its own, with `server` as the root directory. That
  restart drops everyone for a moment and loses any game the server was running, so mention it when
  a push touches `server/`.
- **Rules the server reads from `js/`:** a change to just `js/hockey.js` does not redeploy the server,
  and until it does, players get the slower fallback. Deploy by hand, or change something in `server/`
  too.
- **Hosting limit:** the game server can't run on the Namecheap shared hosting, which doesn't allow
  long-running processes or WebSockets.

## Checks

```
cd server && npm install && npm test   # the game server, its games and tables
node tools/check_games.mjs             # every game hooked up everywhere (blocks the site deploy if not)
python3 tools/check_maps.py            # every room reachable. Read its last line: it exits 0 even on PROBLEMS FOUND
```

Only `check_games.mjs` runs automatically. The browser code has no permanent tests, so try changes
in a browser (see "Testing in a browser").

## Project rules

- **Saved data:** a saved character is a list of places in the lists in `js/art.js`, so only ever add
  to the end of those lists. Never reorder or remove.
- **Wire format:** if what players send each other changes, bump `MP_PROTO` in `js/game.js`.
- **Untrusted input:** other players' messages, saves and addresses can be tampered with. Look names
  up with `inTable`, not a bare `table[name]`, and in server games check what comes from a browser.
- **Test addresses:** anything after a `#` on haakonlife.com acts like a local copy: nothing is saved
  for real and it's in the `test` world. Keep it that way (`BOARD_POSTS`). New testing shortcuts go in
  the README too.
- **A bug ends that game, not everything:** the browser (`layerBroke`) and the server (`crash`, `safely`)
  both work this way. Don't add code that runs outside them with no catch.
- **Controls:** keep to the D-pad or arrows plus A and B on every platform. The user has turned down
  click-to-move, camera rotation and mouse or tap controls in games.
- **Art:** everything is drawn at 32 x 32 on a 640 x 480 screen, laid out in a 320 x 240 view. Use a
  2-pixel outer outline with the light from the top left, and flat colours with a shade and a
  highlight. People keep short legs and fit within one tile. The one exception is a special head thing
  in `BIG32`, like the Christmas Cup's humbug antlers: see "Head things bigger than a tile" in the README. Finer detail in mini-games goes through
  `fine()`, `fineDisc()` and `roundBox()`. Outdoors the look is a rough, very Canadian cartoon:
  flannel, beards, toques, trapper hats.
- **Holidays:** gate with `CHRISTMAS` and `HALLOWEEN`, and `SEASON_FROM` for what stays afterwards.
  Avoid other people's characters: Humbug Sweeper has its own gremlins rather than the Grinch.
- **Writing:** comments, the README and in-game text are plain, friendly English addressed to "you".
  Match what's around them.

## Adding a game

`node tools/check_games.mjs` checks all of this and says what's missing. It reads the code, so keep to
these names. If something is meant to be missing, add it to the exceptions at the top of that file
with the reason.

1. **The game:** `function WidgetGame()` in `js/game.js`, named `...Game` or `...App` so the check sees
   it. It returns `{ doing, music, update(), draw() }` and goes on the stack with `ui.push(WidgetGame())`.
   It closes with `remove(self)`.
2. **The score:** call `saveBest('widget', score)` when it ends. Add `widget` to `BOARDS` and to a page
   in `FAME_GROUPS`. A win-or-lose game with no board goes in `NO_BOARD` in the check.
3. **What you're doing:** `doing: 'widget'` in the game, and a label in `MP_DOING`.
4. **What starts it:** a tile in `GAMES` (in `useTile`), `PLANT_GAMES` or `YARD_GAMES`, a coworker in
   `OFFERS` (in `talkTo`), or a program in `PROGRAMS`. A new tile also goes on the map in
   `tools/build_maps.py`: run that, then `check_maps.py`.
5. **The shortcut:** add it to `const GAME` near the end of `js/game.js`, for `#play&game=widget`.
6. **Head-to-head, if it is:** an entry in `VERSUS`. With `server: true`, the same key in
   `server/games/index.js`.
7. **The manual:** the "Mini-games" list in the README and the `&game=` names under "Testing".

## Games that might go multiplayer

Keep the rules separate from drawing and keys, as `js/hockey.js` does, so the same rules run in the
browser and on the server, and tests can cover them. Use this for any new game that might ever be
played live. Pong, Forklift Rush and the snowball fight don't work this way: their server modules
keep their own copy of the rules, which has to be kept in step by hand. Don't copy that for a new game.

- **The rules:** `js/widget.js` holds `window.WIDGET = (function engine() { ... })();`. No `document`,
  `ctx`, `pressed`, `Math.random` or `Date.now`: randomness comes from a seed and time is counted in
  ticks. The header of `js/hockey.js` is the shape to follow: `create(map, { players, seed })`,
  `g.step(inputs)` with plain data for inputs, `g.save()` and `g.load()` as plain JSON, `g.events` for
  sounds, players marked `ai` for the computer to play, and `VERSION` so a browser can tell whether
  the server has the same rules.
- **The browser:** `WidgetGame` in `js/game.js` reads keys, calls `step` and draws. Add the file to
  `FILES` in `index.html` and to `tools/test.html`, in the same order.
- **The server:** a module in `server/tables/` (anyone can join) or `server/games/` (a two-player
  challenge), listed in that folder's `index.js`. It loads the rules with `vm`, as `load()` does in
  `server/tables/hockey.js`, and decides what really happens.
- **The tests:** `server/test/widget.test.js` plays the rules with no browser, as `hockey.test.js` does.

## Testing in a browser

- **The test page:** `tools/test.html#play&game=NAME` stubs the audio, shows made-up leaderboards and
  sends nothing (`&board=live` reads the real boards, still without sending). It has no other players
  unless you add `&server=ws://localhost:8080`. The README's "Testing" and "Shortcuts" list the rest.
- **Screenshots:** `tools/shot.sh out.png "play&game=snake&ticks=60"` (Firefox and Python's Pillow).
- **Driving it:** run `firefox --headless --no-remote --profile "$(mktemp -d)" --remote-debugging-port=PORT`,
  and from Node 22 or newer connect a `WebSocket` to `ws://127.0.0.1:PORT/session`. That's WebDriver
  BiDi: `session.new`, `script.addPreloadScript`, `browsingContext.create`, `.navigate` and
  `.captureScreenshot`, `script.evaluate`. In the page, `window.GAME` has `press`, `release`, `warpTo`,
  `P`, `mp` and `hockey`, and `problemWhere()` says what's open.
- **Random input for every game:** in a preload script, replace `requestAnimationFrame` and
  `performance.now` with a fake clock running 100 ms a frame, and press random keys through
  `GAME.press` and `GAME.release`. 1800 frames a game takes about 2 minutes for all of them. Count
  `console.error` calls: the game catches its own errors, so `window.onerror` won't see them.
- **Hosted-only code:** set `network.dns.localDomains` to `haakonlife.com` in the profile's `user.js`,
  serve the repo locally, and open `http://haakonlife.com:PORT/`. Stub `fetch`, `WebSocket` and
  `navigator.sendBeacon` in a preload script first, because otherwise this reaches the real database.
- **The live server:** its `test` world is safe to connect to. Real players are in `live`.

## Gotchas

- **Headless Firefox:** use a fresh profile each time and `timeout -k`. It can hang on exit after games
  with music, and a stuck one keeps its profile locked. `--screenshot` fires at the load event, so it
  misses anything set up later, and never finishes for `game=dance`: use WebDriver BiDi for those.
  Headless Brave hangs even on a blank page.
- **Stack traces:** Firefox calls an object's methods just `update@` or `draw@`, with no owner. To
  inject a fault in a mini-game, go by `layerUpdate` or `layerDraw` in the stack.
- **Crash tests:** `node:test` swallows uncaught errors from a server started inside the test, so a
  crash test passes on broken code. Run the server in a child process (`server/test/robust.test.js`),
  and check a new crash test fails on the old code.
- **Shell:** Claude Code's shell here is zsh, so `for g in $LIST` doesn't split: use `bash -c`. Never
  `pkill -f` a pattern that also appears in your own command, or it kills your own shell.
